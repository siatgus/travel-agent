# 智能旅行规划助手 · 企业化路线图（评审稿）

> 2026-10-30 · 现状：单机演示版（本地双服务 8787/8788，SQLite 知识库，DeepSeek 接入，零第三方依赖）。
> 本文回答一个问题：从"本机能跑的 demo"到"能对外收费、能扛住真实用户"的企业应用，缺哪些东西、按什么顺序补。

---

## 〇、一句话结论

企业化不是"加个登录页"，而是**四条线同时升级**：

1. **信任线**：账号体系 + 数据合规 + 内容安全（没有这条，国内对外服务是违法的）
2. **成本线**：LLM 网关 + 额度计费 + 限流（没有这条，每个用户都在烧你的 API key）
3. **规模线**：数据库/缓存/部署形态升级（SQLite + ThreadingHTTPServer 扛不住并发）
4. **价值线**：行程沉淀 + 交易闭环（没有这条，用户用完即走，收不到钱）

---

## 一、账号与用户体系（信任线的地基）

### 1.1 注册登录

| 方式 | 优先级 | 说明 |
|------|--------|------|
| 手机号 + 短信验证码 | P0 | 国内互联网的默认心智，也是防薅羊毛的第一道闸 |
| 微信登录（小程序/公众号 OAuth） | P0 | 旅行场景天然在手机端，微信是最低摩擦入口 |
| 账号密码（可选补充） | P1 | 密码哈希必须 argon2/bcrypt，禁自造加密 |
| 邮箱注册 | P2 | 面向企业差旅客户（私有化部署时常用） |
| 企业 SSO（企业微信/钉钉/OIDC） | P2 | 服务 B 端时的采购加分项 |

要点：
- **Token 设计**：短效 access token（JWT，~30min）+ 长效 refresh token（可吊销、可按设备管理），支持"多端登录管理/强制下线"。
- **找回密码/换绑手机**：上线第一天就要有，否则客服会被淹没。
- **实名/风控钩子**：注册送额度的产品必须留风控位（同设备/同支付账号识别），否则免费额度会被脚本薅穿。

### 1.2 角色与组织

- RBAC 三级起步：**普通用户 / 运营（用现有管理后台）/ 平台管理员**。
- B 端要预留**组织（租户）**概念：企业客户下有成员、组织额度、组织级偏好（如差旅标准：高铁二等座上限、酒店星级上限）。这直接决定数据库每张表要不要从第一天就带 `org_id`。

## 二、LLM 网关与额度计费（成本线的核心）

### 2.1 从"直连"到"网关"

现在的链路是 server → llm.py → DeepSeek 直连。企业化必须收口成一个 **LLM Gateway 模块**，职责：

- **Key 收归服务端**：用户不再自带 key（管理后台的模型设置降级为"平台管理员配置"），用户 key 从此是平台资产，加密存储（KMS 或至少主密钥加密落盘）、支持轮换。
- **多供应商路由 + 故障转移**：DeepSeek 挂了自动切 Kimi/通义；按"任务等级"选模型。
- **统一计量**：每次调用记录 `user_id / 模型 / prompt_tokens / completion_tokens / 折算成本(分)`，落库。这是后面一切计费、额度、毛利分析的数据源。
- **内容安全钩子**：进出各过一道审核（见 4.2）。

### 2.2 额度体系（新用户免费额度怎么设计）

建议用**积分（credit）而不是裸 token** 做计量单位：不同模型单价不同，积分 = token × 模型系数，商业上灵活得多（换模型不用改价格体系）。

**新用户免费额度参考方案：**

| 项 | 建议值 | 理由 |
|----|--------|------|
| 注册赠送 | 500 积分 ≈ 15~20 次"完整规划" | 够体验全流程并产生 1 次真实出行意愿，不够无限白嫖 |
| 有效期 | 30 天 | 制造紧迫感，促转化 |
| 免费档模型 | deepseek-chat 级（便宜档） | 免费用户体验有保证，成本可控 |
| 每日封顶 | 免费用户 3 次/日完整规划 | 防一天内烧完+防脚本 |
| 邀请奖励 | 双方各 +200 | 增长引擎，但要有风控上限 |

**预扣-结算机制（关键实现细节）：**
1. 请求进入 → 按历史均值**预估**本次消耗，先冻结（预扣）；
2. LLM 返回 → 按实际 usage 结算，差额回补/补扣；
3. 额度不足 → 提前拒绝并引导充值，**绝不允许扣成负数后追债**。

### 2.3 计费模式（三选一或组合）

1. **订阅制**（推荐起步）：免费 / 个人版 ¥19 月 / 家庭版 ¥49 月，按月给积分包，简单、现金流可预期；
2. **按量充值**：积分充值包，适合低频用户；
3. **B 端私有化买断 + 年维保**：差旅管理公司/旅行社场景，客单价高、无 C 端合规压力（但仍需内容安全）。

## 三、限流、稳定与架构升级（规模线）

### 3.1 必须加的中间件（在业务代码之前）

- **限流**：令牌桶，按 `user_id`（主）+ `ip`（辅）双维度；免费/付费不同阈值。
- **并发闸**：单用户同时 1 个规划任务（编排器会打 OSRM/天气 API，现在全局锁的做法在多用户下要改成按用户锁）。
- **队列化**：完整规划是重操作（LLM 多轮 + 外部 API），应丢进任务队列异步执行 + 前端轮询/SSE 推进度，而不是让 HTTP 请求挂 60 秒。
- **熔断降级**：天气/OSRM/LLM 任一外部依赖挂掉，走规则降级（现有 llm.py 的静默降级哲学直接复用）。

### 3.2 基础设施升级清单

| 现在 | 企业版 | 说明 |
|------|--------|------|
| SQLite | PostgreSQL | 多用户并发写、备份、主从；表结构改动小，kb.py 的表设计基本可平移 |
| 进程内存 Session | Redis | 多实例部署前提；限流计数、任务队列也顺手用它 |
| ThreadingHTTPServer | FastAPI + uvicorn（容器化） | 异步 + 自动文档 + 中间件生态；agent 编排核心逻辑可原样搬 |
| 本地文件（.kb.db、prefs） | 对象存储 + 数据库 | 行程导出 PDF、用户头像等 |
| 手工部署 | Docker Compose → K8s（后期） | 环境一致性；私有化交付时 Docker 是客户要求的标配 |
| print 日志 | 结构化日志 + APM | user_id 贯穿链路，排查"用户说失败了"必备 |

### 3.3 可以保留的资产

- **编排器 + 校验层**（agent/dialogue/llm 的白名单校验哲学）——这是产品核心竞争力，架构换壳不换芯；
- **SQLite 知识库 → 平移成 PostgreSQL 的 POI 库**，管理后台改造为运营后台；
- **测试体系**（eval/dialogue/llm/server/kb/admin 六套）——企业化的每一步重构都靠它兜底。

## 四、合规与安全（国内对外服务的硬门槛）

### 4.1 资质

- **ICP 备案**（网站/小程序必须）；
- **生成式 AI 合规**：按《生成式人工智能服务管理暂行办法》，面向公众的生成服务需要算法备案/登记，模型需在已备案名单内（DeepSeek 已备案，走它的 API 有利）；自身服务还要过安全评估；
- 若做小程序：小程序类目资质（旅游服务类可能要求旅行社业务经营许可证，**需提前确认类目政策**）。

### 4.2 内容与数据安全

- **内容双审**：用户输入、模型输出都要过敏感词/审核（可接腾讯云/阿里云内容安全 API，几十块能起步），拦截违法有害内容——这是生成式 AI 备案的硬性要求；
- **个人信息保护**：隐私政策 + 用户协议上线首日必须有；数据最小化收集；用户注销要能真删；
- **密钥与敏感数据**：API key 加密存储、日志脱敏（手机号打码）、HTTPS 全站、管理后台加登录+操作审计；
- **等级保护**：对外经营建议过等保二级（B 端客户招标常问）。

## 五、产品价值升级（让用户留下来、付钱）

按"先有留存，再有交易"排序：

1. **P0 行程沉淀**：注册用户的行程永久保存、再次编辑、生成分享页（带裂变属性）；
2. **P0 用户偏好中心**：现有 PreferenceMemory（.user_prefs.json）升级为数据库档案，用户可查看/修改"系统对我的了解"（透明感是信任来源）；
3. **P1 数据增强**：火车票/机票实时余票票价（接商业数据源，12306 无官方 API）、酒店比价——出方案从"参考"变"可执行"；
4. **P1 交易闭环**：接 OTA 分销（携程联盟/美团等 CPS 起步最轻），用户点"预订"跳转，先赚佣金再做自营；
5. **P2 支付**：微信/支付宝 native 支付 + 对账 + 退款 + 发票；
6. **P2 协作与多城**：多人共建行程（结合组织体系）、多城环线编排（P1 遗留技术债，企业化时还上）。

## 六、管理后台的升级方向

现有 admin.py 是"数据管理"，企业化后扩为**运营后台**（独立权限）：

- 用户管理：查询/封禁/手工补额度/发券
- 财务看板：积分消耗、模型成本、毛利（LLM 网关的记账直接出报表）
- 内容审计：被内容安全拦截的记录复查
- 运营配置：模型路由开关、限流参数、活动配置（均热生效——沿用现在的文件指纹热切换模式）

## 七、建议的里程碑

| 阶段 | 目标 | 关键交付 | 判断标准 |
|------|------|----------|----------|
| **M1 · 能上线的最小闭环**（约 4-6 周量级） | 100 个种子用户能安全地用起来 | 手机号注册登录、积分账户+预扣结算、LLM 网关（Key 收归+计量+内容审核）、PG/Redis、容器化部署、隐私协议、ICP 备案启动 | 1 个用户烧不穿你；备案材料齐 |
| **M2 · 能收钱** | 首批付费 | 订阅套餐+支付、行程持久化/分享页、运营后台（用户+财务看板）、限流精细化 | 有陌生人主动付费 |
| **M3 · 能闭环** | 用行程赚钱 | OTA 分销预订、实时票价数据、小程序端、企业 SSO/组织额度 | 预订转化率 > 0 |
| **M4 · 能卖软件** | B 端第二曲线 | 私有化交付包（Docker）、组织/差旅标准、等保 | 签下第一个企业客户 |

## 八、最容易被低估的三件事（风险提示）

1. **免费额度的风控成本 ≈ 额度本身的成本**。脚本薅羊毛是上线第一周就会发生的事，手机号验证只是及格线。
2. **备案与算法合规是按"月"计的流程，不是按"天"**。ICP + 算法备案要在写第一行后端代码时就并行启动，否则产品好了上不了线。
3. **LLM 成本模型必须先于定价**。先跑两周真实计量数据（M1 的网关记账），知道"一次完整规划真实烧多少分钱"，再定 ¥19 还是 ¥29——拍脑袋定价是 SaaS 亏损的第一大原因。
