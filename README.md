# 智能旅行规划助手 · 提示词工程包

一个可运行的智能体原型：提示词、工具契约、混合编排器、质检规则、评测集齐全。拆开能单独用，合起来是一个完整 Agent。

## 跑起来

### 本地部署（浏览器聊天界面）

```bash
python scripts/start_agent.bat     # Windows（双击也行）
./scripts/start_agent.sh           # macOS / Linux
# 等价的手动方式（项目根执行，src 布局）：
PYTHONPATH=src python -m travel_agent.server   # 默认 http://127.0.0.1:8787，--port 改端口，--open 自动开浏览器
```

纯标准库零依赖，Python 3.10+ 即可；只绑 127.0.0.1，不对局域网暴露。
运行时数据统一落在项目根 `data/`（可用环境变量 `TRAVEL_DATA_DIR` 整体重定向）。

启动时会先探一次 `/api/health`：端口上已有实例就直接退出并提示，不重复启动。
（Windows 的 `allow_reuse_address` 会让第二个进程也 bind 成功，结果两个进程抢同一端口、
请求落到旧的那个，改了代码却"没生效"。）

接口：`GET /`（聊天页）、`GET /api/health`、`POST /api/chat`（{sid, message}）、
`POST /api/reset`（彻底删除该会话）、`GET /plan/{sid}`（最近一次方案的完整 HTML 行程页）、
`GET/DELETE /api/conversations[/{sid}]`（历史行程：列表 / 完整对话回放 / 删除，需登录）。

**历史行程与自动保存**：上下文范围 = 用户产生的一次对话（一个 sid 一个 Session）。
登录后每轮对话自动存档到 SQLite（首轮建档 = 自动保存为一次行程，含完整对话内容与方案）；
顶栏「历史行程」可回看任意一次对话、点开继续聊、或删除。重启后按存档续聊，行程页从库里兜底。

### 测试账号（不限额）

想反复验证流程又不想反复充值，建一个不限额账号：

```bash
PYTHONPATH=src python -m travel_agent.auth --unlimited 19900000000        # 建/升级为不限额账号（默认 500 起始余额）
PYTHONPATH=src python -m travel_agent.auth --unlimited 19900000000 --credits 5000
PYTHONPATH=src python -m travel_agent.auth --list                         # 列出所有不限额账号
PYTHONPATH=src python -m travel_agent.auth --revoke 19900000000           # 撤销，回到普通账号
```

然后在网站上用这个号码走验证码登录即可（演示模式验证码会回显），顶栏显示「∞ 额度」。

不限额 ≠ 不记账：余额、每日上限、模型花费都不再拦截，但每次调用仍写 `ledger` 与
`usage`——后台的 token 消耗、任务类型、用量统计一条不少，只是结算时把预扣全额退回，
余额回到调用前。

### 知识库（SQLite）

- 库文件 `data/.kb.db`，纯标准库 sqlite3，零依赖；首次启动自动从核实数据播种（幂等）
- 工具层 `search_poi / search_hotel / search_transport` 与 `serviceable_cities`
  **优先读知识库**，库不可用（只读 .pyz、文件损坏）时静默回落静态数据，规划能力不降级
- 每条数据带 `source`（seed / manual / overpass / auto-fetch / auto-fetch-llm）与 `updated_at`，看板展示新鲜度
- 管理后端新增一个城市的 POI 后，智能体立刻能对它出完整行程（交通/住宿缺数据时如实标注假设）

### 陌生城市自动补全（autofetch.py）

用户说的城市不在库里时，不再回一句"我这边没有数据"：

1. **Overpass（真实 OSM）**：按城市包围盒抓景点与住宿，写库（`source=auto-fetch`），门票按 `fee` 标签、酒店价按星级估算
2. **模型兜底**：Overpass 不可达时，让模型列出该城市景点及坐标，**坐标离城市中心超过 60km 一律丢弃**（防幻觉），写库（`source=auto-fetch-llm`）
3. **补不到才降级**：地名解析不出、上游无返回 → 如实说明并列出可服务城市，绝不排空行程
4. 方案末尾附 `> 数据说明：` 写清哪些是刚补的、哪些是估算值；`/api/chat` 同时在 `fetched` 字段返回补全结果

约束与开关：省份/大区（云南、新疆、华北）不算城市，只追问具体城市；同一城市只抓一次，
失败结果与 Overpass 熔断各缓存一段时间（避免每次说话都等一遍超时）。

```bash
TRAVEL_AUTOFETCH=0              # 关闭自动补全（离线演示/CI）
TRAVEL_AUTOFETCH_TIMEOUT=15     # 整次抓取总预算（秒），超时即换下一档数据源
TRAVEL_AUTOFETCH_MAX_POIS=60    # 单城最多入库景点数
```

## 提示词为什么这样拆

**主提示词只做决策，不写死内容。** 它定义「什么情况该追问」「什么情况该调工具」「输出长什么样」，业务知识留在工具返回的数据里。换城市、换品类只改数据，不动提示词。

**流程显式化。** 五个 Step 是硬顺序。智能体最常见的失败是"信息不够就硬编一份行程"，所以 Step 2 把缺口判定单独成一步，并规定追问上限 2 轮、第 3 轮必须带假设出方案——同时避开无限追问和硬编两个极端。

**自检清单独立成节，且全部可判定。** 九条都是可执行断言（有没有用餐点、预算对不对、闭馆日冲不冲突、景点是否拖到深夜、午餐时段对不对），不是"检查是否合理"。`agent.py::self_check()` 是这套清单的程序化版本，`eval.py` 直接断言它。

**禁止项写得比允许项具体。** 反模式一节列的五个 ❌ 都来自真实对话里的坏输出（每天 6 个景点、把估算说成确定值），比"请保持专业"有效得多。

## 编排器：为什么不做成纯规则或纯 LLM

纯规则只会"按区域取前 N 个"，解释不了为什么去这个不去那个；纯 LLM 会排出地理上不可行的路线（上午城东、下午城西）。所以拆成四段：

```
候选生成（规则）→ 打分排序（可解释权重）→ 贪心成团（距离≤15km）→ 时间轴装配（真实距离→交通耗时）
```

关键实现点：

- **硬约束是否决，不是扣分。** 恐高、带 3 岁幼儿这类约束一旦只做降分，景点照样会以低分挤进候选。`veto()` 直接把它踢出候选池，并在 `--explain` 里显示否决理由。
- **紧迫度决定顺序。** 闭馆早、耗时长（如 16:00 关门、要玩 4 小时的索道）先占上午时段，而不是按分数排。
- **装不下就顺延，不是硬塞。** 算出来赶不上闭馆的景点，移到次日；只有全程都塞不下才算冲突。
- **交通耗时有出处。** 每段交通按两点直线距离估（≤0.8km 步行、≤3km 打车、更远按 30km/h），所以不会出现"步行 18 公里"这种假行程。
- **留白也要写出来。** 空档超过 2 小时会插入"自由活动"，不硬凑景点——这是"不想太赶"用户的实际需求。

权重都在 `composer.WEIGHTS` 里，改一个数就能看到 `eval.py` 的结果变化，这是可调优的前提。

## 接大模型：让它做判断，不让它做创作

`llm.py` 只让模型干两件事：抽槽位、重排候选。两件事的输出都被钉死在闭集里。

**分层是核心。** 用户的每一句话，强度是不一样的，混在一起就会互相打架：

| 层级   | 例子         | 实现                     | 能不能被推翻      |
| ---- | ---------- | ---------------------- | ----------- |
| 硬约束  | 恐高、带 3 岁幼儿 | `veto()` 踢出候选池         | 不能，模型也不行    |
| 明确需求 | "一定要去喜洲"   | `must_visit` 先占位，不参与打分 | 不能，越过距离限制也排 |
| 软偏好  | "想环洱海拍照"   | LLM 重排加成               | 只在分数接近时生效   |
| 默认   | 其余         | 规则打分                   | —           |

**三条工程约束**（对应接模型时最常翻车的三处）：

1. **输出必须过校验才准进管道。** 枚举、类型、日期、白名单逐项检查，`"4天"`/`"4,500元"` 清洗成整数，编造的硬约束直接丢弃并记 warning。
2. **校验失败要回灌重问，不是直接放弃。** 第二次请求带上具体错误（"days=99 超出合理区间"），一次重问能救回大部分格式问题。
3. **两次都失败就静默降级到规则版。** 用户不该为模型的格式问题多等一轮，也不该看到空白。降级原因记在 `CallRecord.degraded` 里，可观测、可统计。

**重排加成的参数是标定的，不是拍脑袋的：**

| `rerank_bonus` | 实测结果                                         |
| -------------- | -------------------------------------------- |
| 1.2            | 模型排第一的点永远选不上，行程一字不变——重排等于摆设                  |
| **3.0（当前）**    | 同分时模型说了算（索道与洱海同为 10 分，模型头名生效）；差一个吸引力档位时规则说了算 |
| 8.0            | 模型可以推翻整个打分体系，规则失去意义                          |

配套的是衰减曲线：线性衰减下第 3 名还能拿 50%，头名优势被抹平；改成平方衰减后头名拿满额、第 2 名 56%、末位 0，头名才真的算"头名"。

这三条边界写成了 `eval.py` 里的断言（「重排能在同分时裁决」「重排不能推翻一个档位的质量差」），后人调大一个数字就会当场失败——比写在文档里管用。

**降级链完整版**：LLM 抽取失败 → 规则抽取；重排失败 → 规则排序；重排钩子抛异常 → 捕获并继续编排。`test_llm.py` 用脚本化的假客户端（可注入超时、围栏 JSON、幻觉 id、非法枚举）把每条路径都跑了一遍，不需要 API Key，也不需要联网。

## 多轮对话：把提示词的追问规则变成状态机

提示词第 47~50 行写了追问规则，但实现里 `find_missing()` 只打印一句"触发追问"就 return——
  
规则在文档里，不在代码里。`dialogue.py` 补齐了整个闭环，`chat.py` 让你真的聊起来：

```
你：下个月想去云南玩几天
它：「云南」我这边没有完整的景点和酒店数据，能排出具体行程的是 大理、丽江，你想去哪个？
你：大理吧
它：大概什么时候出发？（错开节假日，机票酒店能便宜三成）
你：11月8号
它：打算玩几天？（周边游 4 天最舒服，赶一点 3 天也够）
你：4天，2人，预算6000
它：## 大理 4 天行程 · 起 2026-11-08
    > 假设：未提供出发地，方案不含往返大交通（班次与费用）；定了出发地告诉我，我补上班次并更新预算
```

四个设计决定：

1. **槽位合并区分"说了什么"和"默认值"。** 第二轮用户只说"4 天"，抽取器会把它当成
     
   一个全新需求（目的地空、人数默认 1）。`_explicit_fields()` 判断这一轮真正提到了哪些
     
   字段，只覆盖这些——否则用户每多说一句，之前说的就丢一样。
2. **总预算分"明说"和"派生"。** 先说"一人 3000"再说"2 人"→ 总额重算成 6000；
     
   明说"预算一共 6000"再改人数 → 总额不动。混在一起处理必然错一半。
3. **追问看"有没有答上来"，不看"问过没有"。** 一次只问一件；同一件最多问 2 次，
   第二次必须换说法。早期版本把"问过"记进 `asked_fields` 就不再问，于是用户
   反问一句"你不问我从哪出发吗"，系统手里既没有可问的缺口、也没有答案，直接出了方案。
4. **无数据城市不硬编。** 用户说"云南"（省）时，工具返回 NO_POI，旧实现会排一份
     
   只有交通住宿的空行程。现在先探测数据覆盖，追问到具体城市；问满 2 轮仍不明确才
     
   用默认城市，并在假设里写明。

`test_dialogue.py` 的 39 条断言逐条对应提示词原文（第 47 行一次问一件、第 48 行缺预算
  
给三档、第 50 行问满即带假设），外加从真实对话里抠出来的几条回归：
用户反问时不出方案、模糊回答不重复追、出发地不被抽成「哪里」。

## 评测集

`eval.py` 断言的是**可观测行为**，不是文案：是否追问、是否落在预算内、有没有折返、有没有闭馆冲突、有没有排进不该排的景点。

| 用例         | 断言重点                           |
| ---------- | ------------------------------ |
| 完整需求直接出方案  | 不追问、天数正确、每天有餐、无折返、无闭馆冲突、单日景点≤3 |
| 预算充足       | 落在预算内、不出取舍方案                   |
| 超预算        | 识别超支、≥2 个降本方案且金额有效             |
| 缺天数 / 缺目的地 | 分别命中对应追问槽位                     |
| 忌高海拔       | 不排洗马潭索道                        |
| 带 3 岁幼儿    | 不排高强度长时景点                      |
| 特种兵偏好      | 仍守住地理合理（无折返、每天有餐、单日景点≤5）       |

当前 **23/23 通过**。后 4 条是「重排作用边界」，锁住模型能改什么、不能改什么（见下节）。

它最直接的价值是：这轮改编排器时，它抓出了 4 个我自己没看出来的问题（见下）。

## P0 修复（2026-10-29 下午）

实测「一个人邯郸到上海，下个月一号出发，五天时间，预算5000」暴露的三个缺口：

1. **槽位抽取**：新增中文数字解析（`cn_to_int`，「五天」可识别）、无"从"字的路线抽取
   （「邯郸到上海」能抽出出发地）、「下个月一号」解析到具体日（不再折算成第二个周六）；
   具体日期已过的自动顺延明年。出发地查不到班次时如实标注假设，不再静默按默认城市算 0 元交通。
2. **偏好记忆接通**：`Session` 之前收了 `memory` 却从未使用；现在每轮把持久化的
   硬约束并入槽位，`server.py` 默认挂上 `data/.user_prefs.json`，重启不丢。
3. **部署层测试**：新增 `test_server.py`（9 条）——起真实服务走 HTTP 全链路，其中
   "求值后页面 JS 必须 node --check 通过"专门防住本次的「页面字符串求值产生非法 JS」问题。
   另修「还差 0 件事」尬问：没有可问项时直接带假设出方案。

## 可视化行程页

`render_html.py` 把编排结果渲染成单文件 HTML（无外部依赖，双击即开，可直接打印成 PDF）：

- **预算**：横向堆叠条 + 分类图例，金额差异大时比饼图更准
- **路线**：等距圆柱投影的手绘感示意地图，按天着色、编号、标签自动避让；只画点位与连线，不涉及行政边界，规避地图数据合规问题
- **每日行程**：时间轴表格，交通耗时、预约提醒、雨天调整都来自编排器的真实计算
- **质检结果**：九条自检的实时判定，*fail* 一目了然

生成前会先过一遍缺口判定——信息不足时拒绝生成，与主流程行为一致。

## 已知边界

- 真实数据只覆盖大理、丽江（POI/酒店/班次），杭州仅作出发地；其余城市返回 `CITY_NOT_FOUND`，用于验证降级路径。
- 真实票价/房价为 2026-10-29 查询口径，节假日上浮 30%~50%；班次执行"一日一图"，以购票日实际为准。
- OSRM 耗时为正常路况，未含节假日拥堵；断网时自动回落到"直线距离×1.3"估算并在行程中降级。
- 行程天数超过 5 天时，POI 池会不够用，后几天可能出现空档——真实场景需要更丰富的 POI 数据。
- 重排只覆盖景点顺序，不涉及住宿与交通；模型无法新增景点（白名单强制），也无法突破距离与营业时间约束。
- `save_preference` 写的是工具层内存字典；编排层的 `PreferenceMemory`（`.user_prefs.json`）已接入会话与服务端，跨重启保留硬约束。
